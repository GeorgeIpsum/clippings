# Memory benchmark: 2026-09-23

How much memory the Rust side of Clippings uses, where it goes, and
whether it stays flat. There is no VS Code extension yet (plan 3), so
"everything running" is the release binary: `clippings lsp`, which the
extension will keep running for the whole editor session, `clippings
watch` and one-shot `clippings scan`.

Every number below is **measured** unless it is labelled **estimate**.
Sizes are binary units: 1 MiB = 1,048,576 bytes, 1 KB = 1,000 bytes for
per-item costs.

## Summary

- **Typical.** On the tilliX default scan set (1,783 files admitted, 489
  todos) the server's physical footprint is **27 MiB** after the first
  tree, of which **3.5 MiB** is live heap. With 20 source files and a
  10.3 MB file open and edited, the footprint is **60 to 75 MiB**, with a
  live heap of 13 to 23 MiB.
- **Wide set.** On tilliX with hidden files on and ignore files off
  (4,497 files, 2,848 todos) the footprint is **51.5 MiB** after the
  first tree. It rises to **109 to 129 MiB** with a 48.4 MB file open and
  edited. The spec's 150 MB target (section 13) is met by footprint.
  RSS is not a usable number on macOS: it reached 550 MiB in the same
  session (see "Method").
- **Scaling.** Steady memory follows the number of todos, not the number
  of files. A file without todos costs nothing once a scan ends. Each
  todo costs about **270 to 370 bytes in the index and 4 to 7 KB in the
  tree view** when the workspace path is as short as tilliX's (23
  characters), and 12 to 14 KB in the view when it is 100 to 110
  characters. At 60,000 todos under a 110-character path the server's
  footprint is 777 MiB, and 1.2 GiB after one rescan. The view
  dominates: node IDs repeat the absolute path at every folder level and
  each ID is stored seven times.
- **Flat under churn and across rescans.** The live heap does not grow.
  It stayed within ±0.1 MiB over a 30-second churn (31 watched-file bursts
  and 372 edits) and over 100 and 400 rescans. `heap` counted the same
  blocks at rescan 20 and rescan 400: 16,352 and 16,360 blocks, 7,586,928
  and 7,589,968 bytes. The footprint does rise, to a plateau 25 to 70 MiB
  above the live heap. That plateau is memory the system allocator has
  freed but keeps. It is not a leak, and `malloc_zone_pressure_relief`
  returns most of it.
- **Transient peaks** come from the scanner reading whole files, up to
  64 MiB each, on 14 threads: 12 MiB above steady on tilliX, 53 to
  59 MiB on the wide set, and **841 MiB** on a synthetic repository of
  60 MiB files. They also come from view rebuilds, which hold the old and
  new views at once.

## Method

**Process numbers** come from `scripts/memprofile.py`, which drives the
release `clippings lsp` as the LSP client, reusing the framing code of
`scripts/smoke-tillix.py`. Each phase records:

- `ps -o rss= -p PID`;
- the physical footprint and resident size from `proc_pid_rusage`
  (`RUSAGE_INFO_V4`), which is what `footprint PID` and Activity Monitor
  report; `footprint PID` agreed with it to within 1 MiB at every phase;
- the maximum footprint seen by a sampler that reads `proc_pid_rusage`
  every 20 ms, and the process's lifetime peak footprint;
- the thread count from `ps -M`;
- the dirty bytes per `footprint` category (MALLOC_TINY, MALLOC_LARGE and so on).

The **physical footprint is the number to compare.** RSS on macOS also
counts clean shared pages, such as the binary's text and the dyld cache,
and freed pages the allocator has marked reusable, which the kernel can
take back at any time. The gap grows over a session: after the
28-large-file scan, RSS was 849.8 MiB and the footprint 6.8 MiB; after
the wide churn session, RSS was 550 MiB and the footprint 109 MiB.

**Live heap** comes from two examples with a counting
`#[global_allocator]` around `System`
(`crates/clippings-core/examples/support/counting.rs`). No library code
changed.

- `examples/memprofile.rs` builds each component from a real repository
  through the public API: walk and scan, `Index::apply_walk`,
  `View::build`, open documents, decorations, a rescan. It measures each
  component as the bytes freed when it is dropped, and each transient as
  the peak above the bytes live before it. It also accounts for a view's
  bytes by field. With `--fake FILES TODOS ROOT` it builds the index and
  view from made-up paths under any root, without touching the disk.
- `examples/memprofile_lsp.rs` runs the real server loop
  (`server::main_loop::run_stdio`) under the same allocator and logs the
  live bytes every 20 ms. `memprofile.py session --binary` drives it like
  the release server. It serves both the process-versus-heap cross-check
  and the pressure-relief experiment.

**Session phases** (`memprofile.py session`): after `initialize` and before
`initialized`, so before any scan; the first full tree; 10 s idle;
`didOpen` of 20 real source files and the largest text file in the scan
set; 30 s of churn; 2 s and 12 s after churn stops; five `clippings/rescan`
calls, each awaited until `scanning` turns false; `didClose` of every
document; 10 s idle. Each churn cycle does the following:

1. It appends a `// TODO` line to 20 other source files, or restores them, and sends one `workspace/didChangeWatchedFiles` for all 20.
2. It sends 12 `didChange` edits 20 ms apart, alternately inserting and removing a line at the top of one small document and of the large document.
3. It waits 700 ms so the 150 ms buffer rescan and the 500 ms decoration timer fire.

Each cycle nets to no change. The todo count returned to its pre-churn
value in every session.

**The wide set on the server.** The server has no setting to turn ignore
files off: `Settings::core` sets `respect_ignore_files: true`, and only
`scan` and `bench` take `--no-ignore` (spec section 11.3). So the wide
LSP sessions ran on a mirror. The mirror holds APFS clones (`cp -c`) of
exactly the 4,497 files the walker admits with hidden files on and ignore
files off, placed in the scratchpad with no `.git`, so no ignore rules
apply there. With `includeHiddenFiles: true` the walker admits the same
4,497 files and finds the same 2,848 todos in the mirror. One difference
matters: the mirror's root path is 109 characters long against tilliX's
23, and the view grows with root path length (see "Per-component
breakdown"). The mirror's view is 21.6 MiB where tilliX's own is
10.7 MiB. The component numbers for the wide set are therefore taken on
tilliX itself.

### Longer runs: 100 and 400 rescans

`memprofile.py soak` repeats a cycle and samples every 10 or 50 cycles.
All values in MiB.

| Run | Cycles | Live heap first → last (max) | Footprint first → plateau (last) | RSS last |
| --- | ---: | --- | --- | ---: |
| tilliX default, rescan only, no writes (instrumented) | 100 | 3.52 → 3.62 (3.68) | 27.1 → 31 to 35 (32.2) | 72.8 |
| default-set mirror: watched-file churn, 12 edits, rescan (instrumented) | 100 | 6.42 → 6.57 (6.60) | 28.6 → 72 to 78 (76.3) | 121.2 |
| same, with `malloc_zone_pressure_relief` every 1 s | 100 | 6.39 → 6.53 (6.60) | 28.4 → 7.8 to 22.8 (7.8) | 117.8 |
| default-set mirror, rescan only, release binary | 400 | not instrumented; `heap`: 7,586,928 B at cycle 20, 7,589,968 B at 400 | 28.2 → 66 to 73 (71.1) | 111.0 |

The mirror's live heap is 6.4 rather than 3.5 MiB for the same files and
todos, because of its longer root path.

**Result:** no leak. The live heap is flat over 400 rescans, and so is the
set of blocks `heap` walks, which covers every malloc zone, not only Rust
allocations. The footprint rises during the first 30 to 50 cycles, then
holds steady. The rise is allocator retention, and periodic pressure
relief removes nearly all of it.

One false lead is recorded here so nobody chases it: the
`size_in_use` figure from `malloc_zone_statistics` grew by about 48 KB per
rescan. `heap` shows no matching growth in live blocks, so that statistic
is counting something other than live allocations.

## Scaling

### Server process on synthetic repositories

`memprofile.py generate` writes deterministic TypeScript files of about 30
lines, four directories deep (`pkgNN/src/modNN/subN/fileN.ts`). One

- files10k to files100k: ten times the files and todos give 8 times the

- sparse100k has as many files as files100k and costs 34.8 MiB, not

### Index

- Per todo: **372 B** (default), **312 B** (wide), **263 B** (heavy1k).
  `Todo` is 168 bytes inline: five `Position`s, two optional `Position`s,
  four `String`s, an `Option<String>` and a `Vec`. Its strings (tag,
  `before`, `after`, sub-tag) average 46 B. The rest is the `Vec` and the
  `BTreeMap` node overhead.
- Per file with todos: 2.2 KB on tilliX (5.9 todos per file), 1.05 KB on
  the synthetic sets (3 todos per file), which is about 150 B per file plus
  the per-todo cost.
- Per admitted file without todos: **0 bytes** once the walk ends. The
  index keeps only files that have todos. During the walk, each admitted
  file costs about 370 bytes in the `seen` list (path plus `BTreeSet`
  overhead): 37 MB for 100,000 files. It is freed when the walk is applied.

### View

The view costs **5.7 KB per todo** on the default set (4.1 KB per node)
and **3.9 KB per todo** on the wide set. Where its 2.83 MB go on the
default set:

| Part | Bytes | Share |
| --- | ---: | ---: |
| Node ID text, stored 7 times: arena node, `by_id` key, rendered-map key, `ViewNode.id`, parent's children list, `parents` key, `parents` value | 1,319,104 | 47% |
| Node and `ViewNode` structs, hash tables, shaped order | 909,028 | 32% |
| Other arena strings: names, paths, URIs, todo text | 216,727 | 8% |
| Other rendered strings: labels, tooltips, reveal URIs | 170,110 | 6% |
| Unaccounted: allocator rounding, icon cache | about 210,000 | 7% |

Node IDs average 266 characters and reach 632. A node's ID is its
parent's ID plus its own key, and a folder's or file's own key is its
absolute path (spec section 5.12). So an ID repeats the absolute root
path once per level: a todo four folders deep carries it six times. ID
length grows with depth × root path length, and every ID is stored seven
times. `Node` is 448 bytes, because the todo data, status tuple and
optional strings are inline. `ViewNode` is 240 bytes.

### Open documents

- Text is held as a `String` of the same size as the text. The first
  insertion doubles its capacity (`String::replace_range` grows it
  amortised), so an edited document holds up to twice its size. This was
  measured: +10.0 MiB on the 10.3 MB document, and about +48 MiB on the
  48.4 MB document.
- `didOpen` of a large document peaks at 1.5 to 2.7 times its text above
  the previous heap. The JSON-RPC message string, the `serde_json::Value`
  and the `Document` coexist briefly: the heap peaked at 18.6 MiB against
  13.4 MiB after opening 10.4 MB, and at 148.1 MiB against 70.1 MiB after
  opening 48.5 MB.
- Todos of an open document are kept twice, in `Document.todos` and in the
  index's `BufferEntry`: about 300 B per todo each. This is small.

### Decorations

Not retained. For a synthetic 50,000-line buffer with 5,000 todos, the
scan and decoration pass peaked at 2.1 MiB. The ranges map was 131,620
bytes, and the `clippings/decorations` message serialised to 367,788
bytes. The todos of that buffer, which an open document keeps, took
1,445,145 bytes (289 B per todo).

### Pattern, admission and ignore cache

- Pattern: 0.47 to 0.50 MiB, including the regex engines' per-thread
  caches after a 14-thread walk.
- Admission: 0.04 MiB fresh.
- Ignore-rule cache (`IgnoreRules`): one entry per directory an event,
  document close or rewalk asked about, holding four `Gitignore`
  matchers. It is about 0.3 to 0.5 KB per directory: 0.23 MiB for
  tilliX's 83 todo files' directories, 1.34 MiB for about 3,000
  synthetic directories. It is cleared only when an ignore file changes
  or a setting forces a rescan, so it is bounded by the number of
  directories in the scan set.

### Threads, binary and runtime

- Before any scan the process has a 2.4 MiB footprint and 4.2 MiB RSS
  with 4 threads: the scheduler, the `lsp-server` reader and writer, and
  one more. The instrumented binary adds its logger thread. That 2.4 MiB
  is the fixed baseline: the binary's dirty data, dyld, malloc metadata,
  page tables and thread stacks. The binary's 4.0 MB of text is clean and
  shared, so it appears in RSS, not in the footprint.
- Thread stacks are below 0.3 MiB in every `footprint` sample; they are
  too small to list among the categories.
- During a scan: `clippings scan` runs 15 threads (measured), the main
  thread and 14 walker workers, one per core. The server adds its
  detached walk thread and those 14 workers to its 4 (19, inferred). Each
  worker exits when the walk ends.

### Cross-check: live heap against process footprint

On the default set after the first tree, footprint is 27.0 MiB and live
heap 3.5 MiB. The allocator reserves 4.0 MiB for that 3.5 MiB of
requests (`malloc_size` rounding). `footprint` reports the process as
MALLOC_LARGE 10.0 MiB, MALLOC_MEDIUM 6.9, MALLOC_NANO 4.5, MALLOC_SMALL
2.2, MALLOC_TINY 1.6, page tables 0.5, `__DATA` 0.4. The gap:

| Cause | Size |
| --- | ---: |
| Freed but kept by the allocator: the walk's 10.3 MB whole-file read buffer (MALLOC_LARGE), per-thread scan buffers | about 21 MiB |
| Fixed baseline: binary data, dyld, malloc metadata, page tables, stacks | 2.4 MiB |
| Size-class rounding | 0.5 MiB |

With `malloc_zone_pressure_relief` once a second (the instrumented
binary's `CLIPPINGS_MEMLOG_RELIEF_MS=1000`), the same session measured
12.5 MiB after the first tree instead of 27. It measured 20 MiB instead
of 65 to 75 during churn with the 10 MB document open, and 10.8 MiB
instead of 56 to 65 after close.

## Transient peaks

The scanner reads each file whole, up to its 64 MiB heap limit
(`scan_file_with`: `if len <= HEAP_LIMIT { fs.read(path) }`). It does so in
line mode as well as multi-line mode. Only files above 64 MiB are
streamed, and only in line mode. So a walk holds, at any moment, the files
its 14 workers are reading, plus the `seen` list and the results.

| Case | Peak live heap above pre-walk | Process peak footprint |
| --- | ---: | ---: |
| tilliX default, first scan | 12.0 MiB (one 10.3 MB file) | 27.0 MiB |
| tilliX default, rescan with index live | 12.4 to 13.0 MiB | +0.5 MiB over steady |
| tilliX wide, first scan | 52.9 to 58.9 MiB (48.4 MB + 10.3 MB files) | 75.6 MiB |
| files100k, first scan | 42.4 MiB (the `seen` list and results; small files) | |
| bigfiles28: 28 files of 60 MiB | **841.3 MiB** | **716.8 MiB** |

- Bound (**estimate**): 14 workers × 64 MiB = 896 MiB, plus the transient
  copy that `decode` makes for BOM and UTF-16 files, which would raise it
  further. The 60 MiB files came within 6% of it.
- The grep-searcher heap limit (64 MiB) matters only for files over
  64 MiB in line mode, where the roll buffer starts at 64 KiB. Multi-line
  mode reads whole files the same way and skips files over 64 MiB.
- **View rebuilds** hold the old and new views at once: `delta(&self.view,
  &new, ...)` compares them before the old one is dropped. A rebuild
  therefore peaks at about one extra view, 2.8 MiB on tilliX. Every tree
  change triggers one after 50 ms, including one saved file. At 60,000
  todos the extra view is about 680 MiB: the footprint went from 777 MiB
  to 1.2 GiB after one rescan.
- **Rescan** peaks equal a first scan's walk peak plus one view rebuild.
  In the tilliX sessions the footprint moved by at most 0.6 MiB during a
  rescan, because the walk reuses pages the allocator had kept.

## Findings and recommendations

No leak or unbounded growth was found. The problems below are about size.
None were fixed here: library code is unchanged. Savings are
**estimates**.

1. **Tree view IDs dominate steady memory at scale.** At 5 to 14 KB per
   todo, a 60,000-todo monorepo costs 0.3 to 0.8 GiB in its view alone,
   and about twice that during every rebuild. This is the "degrades on big monorepos" failure
   mode, in memory form.
   - *Store each ID once.* Keep IDs as `Arc<str>` in the arena and key
     `by_id`, `nodes`, `children` and `parents` by arena index. This keeps
     one of seven copies of the ID text, so about 40% of the view goes
     (6/7 of 47%): 1.1 MB of 2.8 MB on tilliX, about 270 MiB of 680 MiB at
     60,000 todos. The wire format does not change.
   - *Stop repeating the absolute path.* Use relative own keys, such as
     `d:<name>` and `f:<name>` under a parent whose ID already names the
     path, or a short per-root prefix. Average ID length would fall from
     about 250 characters to about 60 at tilliX-length paths (**estimate**),
     and the dependence on root path length would go away. This changes
     the node ID scheme in spec section 5.12, which the client treats as
     opaque strings, so it is a protocol change for plan 3 or 4.
   - *Shrink `Node`.* Box `TodoData` and the status tuple: about 200 of
     its 448 bytes per node.
   - *Rebuild incrementally, or hold only one full view.* Rebuilding only
     changed subtrees removes the one-extra-view peak per rebuild. This is
     plan 4's "share todo data between the index and the view" work.
   - Together these would bring the view from about 5.5 KB to about 2 to
     2.5 KB per todo at tilliX-length paths (**estimate**: one short copy
     of each ID, 1.1 KB of structs and tables and about 0.6 KB of other
     strings per node, 1.4 nodes per todo). Removing the rebuild peak
     halves the worst case again.
2. **The scanner reads whole files in line mode.** Spec section 5.5 says
   line mode uses the searcher's roll buffer. The code reads every file
   up to 64 MiB into memory, so the walk peak is the sum of the largest
   files being scanned at once: 841 MiB measured, 896 MiB bound on 14
   cores. Fix: in line mode, call `search_reader` for files above a small
   threshold (say 1 MiB). Keep `search_slice` for small files, and for
   BOM and UTF-16 files, or decode those with a streaming decoder.
   Binary detection on a stream is already handled by
   `BinaryDetection::quit`. The walk peak would drop to about 14 × (64 KiB
   to a few MiB), and the freed 10 to 48 MiB read buffers would stop
   lingering in MALLOC_LARGE: 10 MiB of footprint on tilliX, 48 MiB on the
   wide set.
3. **Freed memory is not returned.** Footprint sits 8 to 15 times above
   the live heap on tilliX: 27 against 3.5 MiB idle, 56 against 3.7 MiB
   after close, and a plateau of 71 to 78 MiB against 6.6 MiB in the
   soaks. Fix: on macOS, call `malloc_zone_pressure_relief(NULL, 0)` after
   applying a full walk, after closing documents, and after a large view
   rebuild. Measured with the instrumented binary: 27 → 12.5 MiB after the
   first tree, 56 to 65 → 10.8 MiB after close, and 71 to 78 → 8 to
   23 MiB across the 100-cycle soak. On Linux, `malloc_trim(0)` is the
   glibc equivalent (not measured). libmalloc is expected to relieve
   pressure itself when the system is short of memory (not measured).
4. **Edited documents hold twice their text.** Fix: in `apply_changes`,
   reserve modest headroom (`reserve_exact` with, say, len/16 or 64 KiB)
   before an insertion that would grow the string, or move to a rope.
   Saving: up to the document's size per large edited document, 48 MiB
   for the 48.4 MB file. Every edit already copies the whole tail of the
   string and builds a `LineIndex` of the whole text, so a rope would also
   save CPU.
5. **`clippings watch` keeps the walk's outcome alive.** `watch::run`
   binds `outcome` (all results and the `seen` list) and never drops it
   before its event loop: 0.5 MB on tilliX, about 37 MB for 100,000
   files. Fix: drop it after printing `ready`.
6. **The ignore-rule cache never evicts.** It is bounded by the directory
   count at 0.3 to 0.5 KB per directory, so about 5 to 50 MiB in a
   100,000-directory repository whose every directory sees events
   (**estimate**). Low priority; a size cap or an LRU would bound it.
