# Rust-backed VS Code extensions: how they bridge and ship (v2)

Audience: engineers designing **clippings**, a Rust reimplementation of todo-tree.
Requirements this survey is written against:

- multicore scan of ~50k files;
- incremental index updated on every save;
- results pushed to a tree view and to editor decorations;
- must work under Remote-SSH / WSL / Dev Containers;
- web (vscode.dev) support optional.

What changed since v1:

- v1 deep-read six extensions (Jupyter, C/C++, Java, Tailwind, Continue, Nx Console) and **none of them ships its own Rust**; the Rust LSP extensions were only surveyed from public sources. v2 deep-reads ten Rust-adjacent extensions from local clones under `scratchpad/ref2/`: rust-analyzer, Ruff, Even Better TOML (taplo), Biome, tinymist, CodeLLDB, Slint, Zowe Explorer, Deno, Harper.
- **Eight of the ten ship Rust-compiled code inside the published VSIX**: rust-analyzer, Ruff, Even Better TOML (as wasm32), tinymist, CodeLLDB, Slint, Zowe Explorer (napi-rs `.node`), Harper. **Biome and Deno do not**: both locate a binary the user already has (`node_modules`/PATH/`deno.path`) and spawn it. They stay in the table because their server loops, watcher code and lifecycle handling are still instructive.
- The v1 findings on packaging/lifecycle (cpptools, Java, Jupyter) and on third-party napi-rs/Neon addons (Tailwind, Continue, Nx) are kept in condensed form in section 3; they do not ship Rust of their own.
- Install counts are the Marketplace figures supplied with the task brief (dated 2026-09-22); they were not re-verified from the repos.

Honesty notes:

- rust-analyzer, Ruff, Even Better TOML and Biome notes come from the deep-read inputs supplied to this pass (their `file:line` refs are relative to the clone roots below). tinymist, CodeLLDB, Slint, Zowe, Deno and Harper were read directly from the clones for this pass; every `file:line` cited for them was opened.
- `vscode-languageclient` behaviour is cited from the unpacked 9.0.1 client (`ref2/lc-client.js`, `ref2/lc-node-main.js`, `ref2/lc-fsw.js`), not from memory.
- Where a claim could not be verified from the clone it is marked "not found" or "not verified".

## 5. Patterns to copy for clippings (re-ranked with the new evidence)

1. **Per-platform VSIX with the binary at a fixed path inside the extension, plus a universal "no-server" fallback.** All four bundling LSP extensions do it the same way: build the Rust binary per triple (CI matrix or cargo-dist), copy it into a directory that the `.vscodeignore` whitelist keeps, `vsce package --target <code-target> [--pre-release]`, publish every VSIX with `--skip-duplicate --packagePath`, mirror to Open VSX. Sources: rust-analyzer `RA/.github/workflows/release.yaml:24-69, :111-136, :276-282`, `RA/xtask/src/dist.rs:67-95`, `RA/editors/code/.vscodeignore:1-15`; tinymist `TM/.github/workflows/build-vscode-main.yml:11-37, :115-149, :190-207` and `build-vscode.yml:74-89`; Harper `HARPER/.github/workflows/vscode_plugin.yml:14-100`; Ruff `RUFF/.github/workflows/release.yml:71-202, :277-369`. Keep the no-server universal VSIX (`RA release.yaml:127-136`; `TM build-vscode-main.yml:190-207`) so unsupported platforms can point `clippings.server.path` at their own build. Use Ruff's target list (nine, including alpine-arm64) and rust-analyzer's container choices (`manylinux_2_28` for glibc 2.28, `rust:alpine` with `-C target-feature=-crt-static` for musl). Copy rust-analyzer's `0.3.N` stable / `0.4.N --pre-release` numbering or tinymist's even/odd-minor rule.
2. **Validate the bundled binary at activation by running it, and aggregate every failure into one actionable error.** tinymist's `probePaths` spawns `<candidate> probe` with a 60 s timeout for each of `serverPath` -> bundled -> PATH and throws a single `Could not find a valid tinymist binary.` listing each location and its exit status or spawn error (`TM/editors/vscode/src/lsp.ts:164-209`). CodeLLDB adds a build-time marker file `platform.ok` that is only packaged into the full VSIX (`LLDB/CMakeLists.txt:184, :200`; `extension/install.ts:12-24`), an on-demand DAP self-test (`extension/adapterUtils.ts:77-93`) and a link-dependency whitelist checked in CI (`adapter/CMakeLists.txt:86`, `tools/check_dependencies.py:9-30`). For clippings: ship `bin/platform.ok`, implement `clippings-server probe` that prints its version and target triple and exits 0, run it through tinymist's `probePaths` loop, and refuse to start otherwise. Harper shows the failure mode of skipping this: a missing binary surfaces only as `client.start()` rejecting (`HARPER/packages/vscode-plugin/src/extension.ts:138-150, :167-170`).
3. **Let VS Code own the watcher by default via dynamic `workspace/didChangeWatchedFiles`, keep a `notify` fallback, and treat the two as one `loader::Handle`.** rust-analyzer's `vfs`/`vfs-notify` split is the model: `vfs::loader::Handle { spawn, set_config(Config{version, load, watch}), invalidate(path), load_sync }` (`RA/crates/vfs/src/loader.rs:78-93`); in client mode `Config.watch` is empty, the server registers `RelativePattern { base_uri: <folder>, pattern }` per root (`RA/crates/rust-analyzer/src/reload.rs:569-613, :642-652`) and each `didChangeWatchedFiles` event becomes `loader.handle.invalidate(path)` -> `std::fs::read` -> `Message::Changed` (`handlers/notification.rs:303-319`; `vfs-notify/src/lib.rs:51-53, :193-197`); in server mode the same actor creates a `RecommendedWatcher`, scans with rayon + walkdir and watches symlinked dirs explicitly (`vfs-notify/src/lib.rs:99-278, :300-359`). The switch is automatic when the client lacks dynamic registration (`config.rs:2378-2388`). Slint and Harper show the minimal client-side version (`**/*` with `Create|Change|Delete`, `SLINT/tools/lsp/language.rs:186-224`; delete-only, `HARPER/harper-ls/src/backend.rs:598-616`); Ruff shows why the handler must be incremental (each config event re-walks the whole root, `RUFFRS/crates/ruff_server/src/session/index.rs:263-298`). Biome's `notify` wrapper is the best fallback implementation to vendor: bounded channel, instruction channel with Stop-on-Drop, `select!` loop, macOS/Windows event-kind quirks, non-recursive folder watches batched with `paths_mut()/commit()` (`BIOMERS/crates/biome_service/src/scanner/watcher.rs:88-118, :150-251, :254-312, :452-498`), but note it only runs for Project/TypeAware scans (`session.rs:1115`) and that tinymist inherited rust-analyzer's "untested and quite probably buggy" header while enabling it by default (`TM/crates/tinymist-project/src/watch.rs:1-10`; `crates/tinymist/src/server.rs:118-128`).
4. **Main-loop coalescing, debounce and cancellation from rust-analyzer, Ruff and Biome.** rust-analyzer: `select!` over event sources with a <= 50 ms `try_recv` drain per source so bursts become one turn (`RA/crates/rust-analyzer/src/main_loop.rs:274-313, :443-452`), one `$/progress` per turn (`:1055-1070`), a resettable `crossbeam_channel::after(100ms)` before expensive reloads (`global_state.rs:725-747`), `OpQueue` single-slot state machine for long ops (`op_queue.rs:27-76`), snapshot-per-request with `catch_unwind` + `salsa::Cancelled` -> retry or `ContentModified` (`handlers/dispatch.rs:236-277, :335-390`), and `trigger_cancellation()` on its own thread when inputs change (`global_state.rs:355-363`). Ruff: `RequestQueue` with `Arc<AtomicBool>` tokens, `$/cancelRequest` answered immediately, background tasks re-checking `is_cancelled()`, `Event::SendResponse` dropping late responses (`RUFFRS/crates/ruff_server/src/session/request_queue.rs:56-157`, `session/client.rs:206-227`, `server/api.rs:168-191`, `server/main_loop.rs:100-118`); its `Task::Sync` / `Task::Background` split with a `LatencySensitive` main thread and QoS-mapped worker priorities (`server/schedule.rs:33-74`, `schedule/thread/priority.rs:11-36`) is ~1k lines of MIT code to copy. Biome: 250 ms per-document diagnostic debounce with `scheduled_version`/`rerun_after_current` compare-exchange (`BIOMERS/crates/biome_lsp/src/session.rs:79-101, :477-547`) and version-guarded publish (`:717-730`). Deno: per-URI `DidChangeBatchQueue` so a burst of didChange notifications takes the write lock once (`DENOCLI/cli/lsp/language_server.rs:192-229, :3822-3844`). For clippings' 50k-file scan: run it as one background task that fans out with rayon (rust-analyzer `vfs-notify/src/lib.rs:138-167`; Biome `biome_fs/src/fs/os.rs:175-223`), never as many small pool jobs (Ruff's pool is `bounded(4)` and blocks the main loop when full, `schedule/thread/pool.rs:56`).
5. **Unsaved buffers: Incremental sync, in-memory shadow that beats disk until didClose.** rust-analyzer `MemDocs` + `apply_document_changes` + the `handle_vfs_msg` rule that ignores disk events for open non-library files and re-`invalidate`s on close (`RA/crates/rust-analyzer/src/mem_docs.rs:14-73`, `handlers/notification.rs:58-159`, `main_loop.rs:1003-1013`); Ruff's `Arc::make_mut` copy-on-write so background snapshots never block edits and its UTF-8 > UTF-32 > UTF-16 encoding negotiation (`RUFFRS/crates/ruff_server/src/session/index.rs:536-541`, `edit.rs:19-32`); Biome's `reindex_file` from disk on close (`BIOMERS/crates/biome_service/src/workspace/server.rs:4093-4110`); tinymist's `save_source` disk re-check because notify can miss the save (`TM/crates/tinymist/src/input.rs:101-115`). Avoid `TextDocumentSyncKind::FULL` + `content_changes.last()` (taplo `documents.rs:95-98`, Slint `language.rs:342-344`, Harper `backend.rs:634-636`) — fine for one small file, wrong for a whole-workspace index.
6. **Client-pull refresh and delta publishing instead of pushing the world.** rust-analyzer republishes only files whose diagnostics changed (`RA/crates/rust-analyzer/src/diagnostics.rs:253-262`; `main_loop.rs:595-605`) and otherwise sends `*/refresh` requests so the editor re-pulls visible views (`main_loop.rs:545-566`); Biome fans an `IndexUpdated` notification to every session through a tokio `watch` channel (`BIOMERS/crates/biome_lsp/src/session.rs:344-360`). For clippings: `clippings/indexChanged { changed: [FileId], removed: [FileId] }` plus a `clippings/items` request the tree view pulls on demand, and per-document `{uri, version, items[]}` pushes for decorations with cpptools-style stale-drop (`CPP/src/LanguageServer/client.ts:2605-2622`).
7. **Custom protocol mirrored on both sides.** rust-analyzer's `lsp_ext.ts` `new lc.NotificationType<Params>("...")` / `lc.RequestType` mirrored by `impl Notification for X { const METHOD }` in `lsp/ext.rs` (`RA/editors/code/src/lsp_ext.ts:30-48, :220-222`; `crates/rust-analyzer/src/lsp/ext.rs:575-590`), custom client capabilities via a `lc.StaticFeature` (`client.ts:303-346`); taplo's `taplo/*` notifications registered with `context.subscriptions` (`TAPLO/editors/vscode/src/extension.ts:27-60`); tinymist's `tinymist/fs/watch` + `tinymist/fsChange` request pair as the template for a client-served filesystem (`TM/editors/vscode/src/lsp.ts:557-600, :922`; `crates/tinymist/src/input/watch.rs:125-133`).
8. **Same Rust crate as WASM for the optional web target, with the filesystem delegated to the client.** Three shipping extensions prove the path and they all agree on its shape: build the server crate to `wasm32-unknown-unknown` with wasm-bindgen (`--target web`), load it inside a Web Worker, wait for a ready message, then `new LanguageClient(id, name, clientOptions, worker)` from `vscode-languageclient/browser`, and give the WASM server a client-served file API. taplo: `Environment` trait with native and JS-callback implementations (`TAPLO/crates/taplo-common/src/environment.rs:13-84`, `crates/taplo-wasm/src/environment.rs:144-354`), `server-worker.ts` with stubbed fs (`editors/vscode/src/server-worker.ts:17-38`), `createBrowserClient` (`client.ts:20-32`). tinymist: `web/server.ts` `initSync(tinymist_bg.wasm)` + `TinymistLanguageServer` bridge and `serverWorkerReady` (`TM/editors/vscode/src/web/server.ts:10-68`), `lsp.web.ts:8-40`, `WatchAccessModel` always selected on non-system builds (`crates/tinymist/src/config.rs:880-886`), `wasm-pack` job (`build-vscode-others.yml:122-135`), `web` VSIX target. Slint: `slint/load_file` request answered with `vscode.workspace.fs.readFile` (`SLINT/editors/vscode/src/browser.ts:64-72`), broad scheme list including `vscode-vfs` and `vsls` (`:40-45`), wasm built in `vscode:prepublish` (`package.json:218-222`). None uses `@vscode/wasm-wasi-lsp`; none is multi-threaded on web. For clippings this means: keep all fs access behind one trait from day one, and expect the web scan to be single-threaded and client-fed.
9. **Shipping napi-rs in a universal VSIX is workable for a small in-process piece.** Zowe ships 11 `keyring.<target>.node` prebuilds inside one universal VSIX and resolves them at runtime by `<platform>-<arch>-<abi>` with musl detected through `process.report` (`ZCLI/packages/secrets/src/keyring/index.js:26-53`), webpack-safe via `__non_webpack_require__` (`:46-49`; `ZE/packages/zowe-explorer/webpack.config.js:83-91`, `russh-native-loader.js`), copied into `prebuilds/` at build time (`scripts/copyPrebuilds.js`) and whitelisted in `.vscodeignore`; load errors are deferred to first use (`DefaultCredentialManager.ts:149-167`); the Rust CI is an 11-target `cross`/QEMU matrix uploading `bindings-<target>` (`ZCLI/.github/workflows/secrets-sdk.yml:35-175`). This is the fallback if clippings ever needs a hot in-process path (per-document decoration scanning) — ship the addon in the same per-platform VSIX, resolve by triple, and never let its absence break activation. Zowe's runtime `unpkg.com` download without a checksum (`NativeSshHelper.ts:38-77`) is the counter-example to avoid.

## 6. Traps observed (v1 merged with v2)

**Binary distribution and validation**

- The only validation in rust-analyzer, Ruff and Biome is a `--version` exit/parse; Slint checks `existsSync`; Harper checks nothing (`HARPER .../extension.ts:138-150`). A corrupt, wrong-arch or non-executable binary surfaces as `client.start()` rejecting with a generic message. tinymist's `probe` loop (`TM .../lsp.ts:179-209`) and CodeLLDB's `platform.ok` marker (`LLDB/CMakeLists.txt:200`) are the two designs that fail loudly and early.
- Executable bits: VSIX unzip and reinstall reuse can lose them; Slint and Biome `chmod 755` at build/copy time (`SLINT nightly_snapshot.yaml:296`; `BIOME/src/biome.ts:329-397`), cpptools on every activation (`CPP/src/main.ts:188-220`). NixOS needs a patchelf'd copy in `globalStorage` (`RA/editors/code/src/bootstrap.ts:225-306`).
- Per-target VSIX means every remote platform needs a matching build or the ext-host gets no binary; rust-analyzer and tinymist ship a no-server universal VSIX and a clear error; Harper and Ruff ship none. Ruff's win32-arm64 VSIX appears to bundle the x86_64 exe (`RUFF release.yml:78-80, :160-163`); Continue's alpine ships glibc and armhf ships arm64 (`R .../prepackage.js:56-61`); Slint has no musl binary at all.
- Marketplace ordering: rust-analyzer's `0.4.N --pre-release` nightly vs `0.3.N` stable is a deliberate hack (`RA/xtask/src/dist.rs:19-40`); tinymist and Ruff use tag/minor parity. Pick one and never let a stable version sort above a pre-release.
- Download-at-runtime: CodeLLDB's bootstrap VSIX downloads the full VSIX from GitHub and installs it (`LLDB/extension/install.ts:27-88`) — workable but adds a first-run network dependency and an unsigned-VSIX path; Zowe downloads `russh.<triple>.node` from `unpkg.com` with no checksum straight into the extension directory (`ZE .../NativeSshHelper.ts:38-77`). Neither is acceptable for a corporate/air-gapped user base; bundle.
- Workspace-supplied binaries (Biome, Deno, Tailwind, Nx) depend on the user's package manager, PATH or version manager shims; Biome needed a hidden `__where_am_i` command to unshim `.cmd` wrappers (`BIOME/src/locator.ts:93-165`) and copies the exe to `storageUri` on Windows because the running file is locked (`biome.ts:272-397`). Not applicable to clippings but shows the Windows lock trap applies to spawned binaries too when the file can be replaced underneath.
- Universal VSIX with everything in it (Slint: six binaries; Zowe: 11 + 7 prebuilds; taplo: two 35 MB WASM copies) trades per-target CI for download size and startup cost; taplo base64-decodes and instantiates tens of MB on every server start (`TAPLO/js/lsp/src/index.ts:36-38`; `editors/vscode/src/extension.ts:17-18` awaits it in `activate`).
- Multi-repo drift: Ruff's extension pins a PyPI wheel hash (`requirements.txt:59-77`); taplo's VSIX contains whatever `@taplo/lsp` yarn resolves, which differs from `js/lsp/package.json` (0.8.0 vs 0.8.1); Zowe's prebuilds come from "the latest successful CI run on this branch" (`prebuildify.sh`). Keep the Rust crate in the extension repo and build it in the same workflow.

**Watching and index freshness**

- `notify` is unreliable enough that every server using it documents workarounds: rust-analyzer's FUSE `Access(Open)` heuristic and symlink watches (`RA/crates/vfs-notify/src/lib.rs:199-233, :330-334`), tinymist's 300 ms missing-file poll and inotify implicit-unwatch fix (`TM .../watch.rs:285-295, :485-500`) plus a didSave disk re-check (`input.rs:101-115`), Biome's `bounded(128)` channel with "notify is intrinsically unreliable" (`watcher.rs:153-161`) and `exists()` re-checks because macOS emits `Modify(Data)` after deletes (`:289-298`). Default to VS Code's watcher (it honours `files.watcherExclude` and works over Remote), keep notify as the fallback.
- Non-recursive per-directory watches (Biome `watcher.rs:465`, tinymist per-file `:438`) explode inotify watch counts on a 50k-file tree; cpptools' `createFileSystemWatcher("**/*")` hits the same Linux 8k default (`CPP .../client.ts:2694`). Use recursive watches or the VS Code watcher.
- Config-file events that trigger a full re-walk without debounce (Ruff `index.rs:263-298`) or a full re-init of every workspace including HTTP fetches (taplo `handlers/configuration.rs:12-29`) are the pattern to avoid; rust-analyzer's 100 ms resettable timer (`global_state.rs:725-747`) and Biome's 250 ms per-document debounce (`session.rs:79-101`) are the pattern to copy.
- Disk events for open documents must be ignored or you clobber unsaved edits (`RA main_loop.rs:1003-1013`); on didClose you must re-read disk (`RA handlers/notification.rs:154-156`; Biome `server.rs:4093-4110`).
- Biome's source watcher is off with the default scan kind (`session.rs:1115`), so index freshness for unopened files silently depends on `didChange` alone — clippings must always scan and watch.
- Full-document sync + `content_changes.last()` (taplo, Slint, Harper) silently corrupts state if a client ever sends incremental changes; taplo's `Mapper` allocates two BTreeMap entries per byte per keystroke (`lsp-async-stub/src/util.rs:127-135`).

**Process model and threading**

- `$/progress` notifications serialise on the VS Code main thread; send at most one per loop turn (`RA main_loop.rs:1055-1070`). Loop turns over 100 ms are logged as bugs (`:632-646`).
- Ruff's worker pool is capped at 4 threads with a `bounded(4)` job channel, so `Pool::spawn` blocks the main loop when full (`RUFFRS .../pool.rs:56`, `CONTRIBUTING.md:10-11`); a 50k-file scan must be one background task that fans out internally.
- Worker-pool panics abort the whole process in Ruff (`pool.rs:76-94`); only request handlers are `catch_unwind`-contained. Biome contains per-file scanner panics into diagnostics (`scanner.rs:845-884`). Wrap per-file work.
- WASM-in-Node (taplo) and the wasm web builds (tinymist, Slint) are single-threaded; taplo's native server also runs all handlers on one `LocalSet` thread under one global `RwLock` (`lsp-async-stub/src/listen.rs:30-32`; `world.rs:80`). Do not copy taplo's server loop for a parallel indexer.
- A shared daemon (Biome) multiplies failure modes: a daemon crash kills every proxy (`daemon.rs:158-174`), `--stop-on-disconnect` only fires after one session initialised (`server.rs:629-647`), the socket is keyed by version only (`unix.rs:26-28`), and tokio stdin reads cannot be cancelled so the proxy `process::exit`s. Per-window stdio is simpler.
- vscode-languageclient keeps emitting `didChangeWatchedFile` after dispose and would restart the client for no reason without a middleware guard (`RA client.ts:23-30`). The default handler stops restarting after 5 crashes in 3 minutes (`LC/lc-client.js:180-191`); a crash-looping binary then needs a manual restart command.
- No `deactivate()`/`client.stop()` (taplo `extension.ts:7-61`) means no shutdown/exit handshake; the child is killed with the host and the index is not flushed.
- Windows: VS Code may hand the server lowercase drive letters (`RA session.rs:175-205`); `.cmd/.bat` need a shell; a loaded `.node` or running exe holds a file lock (Biome, Tailwind, Nx); Python-style helpers must force UTF-8 stdout (`RUFF/bundled/tool/find_ruff_binary_path.py:33-38`).

**Remote and web**

- The VSIX must match the **remote** OS/arch/libc and the extension must run on the remote: rust-analyzer and taplo force it with `extensionKind: ["workspace"]`; Ruff, Biome, Deno, Harper, tinymist rely on the default (`main` only, no `extensionKind`). Slint's `["workspace","ui"]` exists for its GUI preview and sets `DISPLAY=:0` on remote Linux (`SLINT .../extension.ts:48-53`) — not a pattern for clippings. Continue's `["ui","workspace"]` is the wrong order.
- Only `file:` schemes are supported by rust-analyzer, Ruff, taplo, Deno (documentSelectors); virtual workspaces and Live Share are out of scope unless the web/WASM path (Slint's scheme list, `browser.ts:40-45`) is taken.
- `cargo xtask install`-style dev installs do not work into a Remote host (`RA/xtask/src/install.rs:142`); install the target VSIX manually there.
- Containers: PID namespaces hide the editor pid (Deno `parent_process_checker.rs:10-20`), `/tmp` may be unusable for pipes (Java probes and falls back to stdio), locale may be `C` (Java forces `LC_CTYPE`); Biome's cache dir falls back to `env::temp_dir()` when the ProjectDirs cache is not writable (`biome_fs/src/utils.rs:24-35`).
- Web: none of the three shipping web extensions has a filesystem in the worker; taplo stubs `readFile` to reject, tinymist and Slint route reads through the client (`tinymist/fs/watch`, `slint/load_file`). Expect a client-fed, single-threaded scan; `@vscode/wasm-wasi-lsp` remains `0.1.0-pre.9` and unused by any of them. WASM needs Node >= 20 features in the ext-host (taplo bumped `engines.vscode` to `^1.90.0` for `crypto.getRandomValues`).

**Packaging traps carried from v1**

- Ship what you reference (Tailwind stripped `@parcel/watcher` prebuilds its bundle still `require`s); list the VSIX before publishing.
- Every shipped native file must be code-signed per target or it ships unsigned (Jupyter `codesignPaths`).
- Universal PR builds never exercise target pruning (Jupyter); make CI package at least one real `--target` VSIX per PR (tinymist runs its extension tests on linux-x64 and win32-x64 with the bundled binary, `build-vscode-main.yml:47, :177-187`).
- `npm ci --ignore-scripts` or native devDeps try to compile from source (Jupyter, Ruff `release.yml:173`).
- Silent degradation hides a missing binary (Jupyter, Tailwind, Continue); decide up front to surface it loudly (tinymist, CodeLLDB).

## 7. Recommended bridge architecture for clippings

**Recommendation: unchanged in shape, sharpened in detail. A standalone Rust server binary, bundled per platform at `<ext>/bin/clippings-server[.exe]` (nine `vsce --target` VSIXes plus a universal no-server VSIX), spawned by `vscode-languageclient` as an `Executable` over stdio, speaking LSP-shaped JSON-RPC (standard `textDocument/didOpen|didChange(Incremental)|didSave|didClose`, dynamically registered `workspace/didChangeWatchedFiles`, and a small set of custom `clippings/*` requests and notifications), with `extensionKind: ["workspace"]`, and an optional later `web` target that compiles the same server crate to `wasm32-unknown-unknown` behind a Web Worker with a client-served filesystem.**

**Does the new evidence confirm or change v1?** It **confirms** the bridge and transport choice and **changes three details**:

1. *Confirmed — LSP process over stdio via `vscode-languageclient`.* Every Rust-shipping LSP in the set (rust-analyzer, Ruff, tinymist, Harper, and Slint's native path) uses exactly `Executable { command, args, options: { env } }` with the library's default stdio pipes (`RA ctx.ts:232-239`; `RUFF server.ts:290-294`; `TM lsp.system.ts:32-42`; `SLINT extension.ts:204-208`; `HARPER extension.ts:15`), the default `DefaultErrorHandler` for crash restarts, `initializationOptions` for settings, and `lsp_ext`-style custom methods. None of them needed a socket, a pipe, a daemon or an in-process addon for an LSP-shaped workload. The two extensions that deviate do so for reasons clippings does not share: CodeLLDB's reverse TCP + auth token exists because DAP sessions are per-debug-session and the adapter must outlive VS Code's stdio handling (`LLDB .../adapter.ts:21-60`, `reverseConnector.ts:21-60`); Biome's per-user daemon exists to share one index between VS Code windows and the CLI and brings a long list of failure modes (section 6). Zowe shows that an in-process napi-rs addon is shippable in a universal VSIX, but it also shows the cost: no supervisor, deferred load errors, and a temptation to download binaries at runtime.
2. *Changed — validation.* v1 proposed reading `.vsixmanifest` `TargetPlatform` (cpptools). The Rust set shows a simpler and stronger check: run the bundled binary with a `probe` subcommand, time-box it, and aggregate failures across `serverPath` -> bundled -> PATH into one error (tinymist `lsp.ts:164-209`), plus a `platform.ok` marker only present in the full VSIX (CodeLLDB `CMakeLists.txt:200`). Do both; skip the manifest regex.
3. *Changed — watcher ownership.* v1 said "let VS Code own the watcher via dynamic registration". v2 makes that the default but insists on the rust-analyzer shape: one `loader::Handle` abstraction whose client mode registers `RelativePattern { base_uri: <folder>, pattern: "**/*" }` per workspace folder and turns each event into `invalidate(path)` -> read -> `Changed`, and whose server mode is a vendored `notify` actor (Biome's `watcher.rs` or rust-analyzer's `vfs-notify`) selected automatically when the client lacks dynamic registration (`RA config.rs:2378-2388`). The scan and the watcher feed the same `Vfs` change log with content-hash dedup (`RA vfs/src/lib.rs:216-281`), so the index update path is identical for initial scan, save, external change and client-delegated web reads.
4. *Changed — web plan.* v1 pointed at `wasm32-wasip1-threads` + `@vscode/wasm-wasi-lsp`. No shipping extension uses that; taplo, tinymist and Slint all use `wasm32-unknown-unknown` + wasm-bindgen in a Worker with `vscode-languageclient/browser` and delegate file reads to the client (`TM config.rs:880-886`; `SLINT browser.ts:64-72`; `TAPLO server-worker.ts:17-38`). Follow the proven path, accept single-threaded and client-fed on web, and keep every fs call behind one trait (taplo's `Environment`, tinymist's `PathAccessModel`) from the first commit so the web build is a target, not a rewrite.

**Concretely.** The extension activates on `onStartupFinished`, checks `bin/platform.ok`, runs `probePaths([["clippings.server.path", ...], ["Bundled", <ext>/bin/clippings-server], ["In PATH", "clippings-server"]])` with `["probe"]`, then `new LanguageClient("clippings", ..., { run: { command, args: ["lsp"], options: { env: { ...process.env, RUST_BACKTRACE: "1" } } } }, { documentSelector: [{ scheme: "file" }, { scheme: "untitled" }], initializationOptions: <clippings.* settings>, outputChannel })`. The server (`lsp_server::Connection::stdio()`, main loop on a `LatencySensitive` thread, rayon pool sized to physical cores) answers `initialize` with `TextDocumentSync { open_close, change: Incremental }`, registers `workspace/didChangeWatchedFiles` per folder, scans with `ignore::WalkBuilder` + rayon into a `Vfs` change log, keeps `MemDocs` for open buffers with the "client is authoritative" rule, coalesces events per loop turn, debounces rescans with a resettable 100 ms timer, runs per-file extraction under `catch_unwind` with snapshot + cancellation, and streams `clippings/indexChanged { changed, removed }` (tree view re-pulls via `clippings/items`) and per-document `clippings/decorations { uri, version, ranges[] }` (client drops stale versions). Packaging: cargo build per triple (rust-analyzer's container matrix, Ruff's nine targets), copy into `bin/`, `.vscodeignore` whitelist with `!bin`, `vsce package --target`, tests run against the bundled binary on linux-x64 and win32-x64, universal no-server VSIX, `vsce`/`ovsx publish --skip-duplicate --packagePath`, stable/pre-release numbering that always sorts nightly above stable. Index persistence under `globalStorage/<workspaceHash>` with a sha1-named cache directory (taplo `schema/cache.rs:54-131`) and the last tree model in `workspaceState` for warm start.

**Why, in one paragraph.** The v1 recommendation was inferred from non-Rust native servers (cpptools, Java) and from public descriptions of the Rust ones; v2 replaces inference with the code of the five highest-install Rust LSP extensions and finds them converging on the same skeleton, down to identical `ServerOptions` literals and identical reliance on the library's crash policy. The parts of clippings that are harder than a linter — a 50k-file parallel scan, incremental updates on save, external-change detection over Remote — are exactly the parts where rust-analyzer's `vfs`/`vfs-notify`/main-loop design (`RA crates/vfs`, `crates/vfs-notify`, `main_loop.rs:274-313, :443-452`, `global_state.rs:725-747`) and Biome's scanner/watcher (`biome_fs/src/fs/os.rs:175-223`, `scanner/watcher.rs`) already carry the scars, and both are MIT/Apache code that fits behind an LSP stdio bridge without modification. Ruff and Deno add the request-cancellation and didChange-batching pieces that keep the editor responsive while the index churns. tinymist and CodeLLDB supply the two missing lifecycle pieces v1 could only guess at (binary validation and a no-server fallback), and tinymist, Slint and taplo prove that the same Rust crate reaches vscode.dev through a Worker without changing the bridge. The negative evidence is equally consistent: the only extensions that avoid a bundled binary (Biome, Deno) do so because they must track a project-local toolchain, which clippings does not; the only in-process Rust (Zowe) is a tiny keyring shim whose distribution story (runtime unpkg download, deferred load errors) is precisely what a supervisor-less design leads to; and the single WASM-in-Node bridge (taplo) is single-threaded and 35 MB, ruling it out for the primary path. Nothing in the new evidence argues for a socket, a daemon, an addon or WASI; everything argues for a bundled, probed, stdio-spawned Rust server with a rust-analyzer-shaped VFS and a client-owned watcher.
